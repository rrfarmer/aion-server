## Hard contracts (never change during the port)

- MySQL/MariaDB schemas and existing SQL behavior.
- `.properties` config keys and override precedence.
- Binary packet wire formats (opcodes, field order, encoding).
- XML/static-data shape and validation expectations.
- The three-process boundary: `login-server`, `game-server`, `chat-server`.
- Docker-oriented deployment flow.

## Non-goals (for the parity port)

- No gameplay redesign. No re-architecting before parity exists.
- No ORM / Entity Framework — keep direct SQL close to the Java DAO layer.
- No database/format swaps (no JSON/YAML for XML data, no DB replacement).
- No merging the three processes.
- No removing dynamic-handler support.

## Repo layout

- Java (source of truth): `commons/`, `login-server/`, `chat-server/`, `game-server/` (Maven multi-module). Game-server also has runtime content under `game-server/data/handlers` (quests, AI, instances, commands) — application code, not optional data.
- C# (target): `dotnetConversion/` (`.NET 10 LTS`). `src/Aion.{Commons,LoginServer,ChatServer,GameServer}`, `tests/`, `tools/`. Java package → C# folder/namespace 1:1 (`game-server` → `Aion.GameServer`).

## Architecture mapping rule

C# structure mirrors Java structure: one Java file → one C# file, class → class, method → method, packet → one handler. No abstraction Java does not have; no god-class. See the Fidelity Gate in `parity-verification.md`. This rule is the spec — it is what "no slop" means concretely.
